System Design Document: Платформа вторичного рынка книг в Telegram

1. Определение пространства задачи и требований

При проектировании e-commerce систем в мессенджерах, таких как Telegram, критически важно избежать антипаттерна «God Object». Размытие ответственности между обработкой UI-состояний бота и бизнес-логикой ведет к созданию нетестируемых монолитов. Мы будем использовать принципы GRASP (High Cohesion) и SOLID, чтобы разграничить функционал и обеспечить независимое масштабирование компонентов. Это стратегический фундамент для системы, работающей в условиях высокой конкуренции за внимание пользователя, где любая задержка ведет к оттоку аудитории.

Функциональные требования

* Размещение объявления: Создание карточки книги (метаданные + медиа) продавцом.
* Полнотекстовый поиск: Поиск книг по автору, названию и описанию с учетом опечаток.
* Оформление заказа: Резервирование книги и управление жизненным циклом сделки.
* Оплата: Интеграция с платежными шлюзами через Telegram Payments API.

Нефункциональные требования

* Availability (99.9%): Согласно теореме CAP, мы проектируем AP-систему (Availability + Partition Tolerance), обеспечивая доступность при сетевых разделениях, жертвуя строгой консистентностью в пользу Eventual Consistency.
* Latency (< 200ms): Время отклика API-слоя должно быть минимальным для сохранения UX «бесшовного» мессенджера.
* Scalability: Поддержка 100M DAU с использованием горизонтального шардирования и Actor Model.
* Надежность: Гарантированная доставка критических уведомлений и сохранность финансовых транзакций.

Вывод: Совокупность данных требований диктует необходимость распределенной архитектуры на базе микросервисов и виртуальных акторов, способных эффективно утилизировать облачные ресурсы при взрывном росте нагрузки.

2. Оценка нагрузки и ресурсов (Capacity Estimation)

Предварительные расчеты позволяют выявить узкие места (bottlenecks) до написания первой строки кода. Мы ориентируемся на 100M DAU как на целевой показатель.

Расчет QPS (Queries Per Second)

* Чтение (Поиск): 10 запросов на пользователя в день = 1 млрд запросов/сутки.
  * Средний QPS: ~11,500.
  * Пиковый QPS: ~23,000.
* Запись (Объявления): 1% пользователей (1 млн) создает 1 объявление в день.
  * Средний QPS: ~12.
  * Пиковый QPS: ~50-100.

Пропускная способность и хранилище

* Bandwidth (Пропускная способность): При 2 млн фото в день (по 1 МБ) объем входящего трафика составит ~2 ТБ/день. Это требует средней пропускной способности ~23 МБ/с (184 Mbps). В пиковые часы нагрузка может возрастать до 1-2 Gbps, что требует асинхронного пайплайна обработки.
* PostgreSQL: 100 млн объявлений в год по 1 КБ текста = 100 ГБ/год. С учетом индексов (GIN/GiST) объем возрастет до 300 ГБ. Для обеспечения долговечности (durability) обязательна настройка Write Ahead Log (WAL) и мониторинг High Water Mark для управления состоянием реплик.
* S3 (Медиа): Оригиналы + миниатюры потребуют ~800 ТБ дискового пространства в год.

Connective Tissue: Высокий QPS на чтение и значительный объем медиа-трафика делают вертикальное масштабирование невозможным. Мы переходим к проектированию системы с использованием балансировщиков и распределенного стейта.

3. Высокоуровневая архитектура (High-Level Design)

Для реализации системы выбрана микросервисная архитектура с применением Microsoft Orleans (Virtual Actor Model) для управления состоянием сессий пользователей.

Компонент	Зона ответственности	Suggested .NET Stack/Pattern
API Gateway	Роутинг, Rate Limiting, SSL Offloading.	YARP (Yet Another Reverse Proxy)
Telegram Bot Service	Прием Webhooks, парсинг команд Telegram API.	.NET 8 / Minimal APIs
App Builder Service	Управление состоянием многошаговых форм (wizard).	Orleans Grains (Stateful Actors)
Book Recognition	OCR и классификация обложек через gRPC.	.NET 8 / ObjectPool<T> для буферов
Search Service	Полнотекстовый поиск по распределенной БД.	PostgreSQL (Read-only Slaves)
Order/Payment	Транзакции и координация заказов.	Saga Pattern / Outbox

Коммуникация

* Синхронная (gRPC/Protobuf): Используется для взаимодействия между внутренними сервисами, где важна минимальная задержка (Recognition Service).
* Асинхронная (Kafka): Используется для всех событий изменения состояния (Order Created, Image Uploaded).

Connective Tissue: Использование Orleans Grains позволяет хранить состояние "черновика" объявления в памяти, минимизируя дорогостоящие round-trips к базе данных, что критично для производительности при 100M DAU.

4. Асинхронный пайплайн обработки медиа

Обработка изображений — ресурсозатратная операция, которая не должна блокировать поток обработки сообщений бота.

1. Ingress: Bot Service получает file_id и перекладывает задачу в Kafka.
2. Processing: Воркеры, использующие Microsoft.Extensions.ObjectPool для эффективной работы с массивами байтов, скачивают оригинал.
3. Transformation: Генерация миниатюр и оптимизация (resize). Для оптимизации метаданных часто повторяющихся тегов книг используем String.Intern().
4. Storage: Загрузка в S3 и получение публичного URL.
5. Completion: Обновление записи в БД через событие.

В случае сбоя воркер отправляет сообщение в Dead Letter Queue (DLQ). Это гарантирует отзывчивость бота: пользователь видит статус «Обработка...» почти мгновенно, пока система выполняет тяжелую работу в фоне.

5. Механизмы надежности и консистентности данных

В распределенных системах, как отмечает Крис Вудрафф, «ответственность должна быть явной», иначе два узла примут противоречивые решения.

* Предотвращение Double Buy: Используется Optimistic Locking в PostgreSQL. Каждая запись содержит version (Generation Clock). При покупке выполняется UPDATE ... WHERE version = @oldVersion. Если версия изменилась — транзакция отклоняется.
* Transactional Outbox: Чтобы гарантировать, что после создания заказа событие точно попадет в Kafka, мы сохраняем бизнес-сущность и событие в одной БД-транзакции. Background worker (Outbox Publisher) затем надежно пересылает события.
* Saga Pattern (Choreography): Управляет процессом покупки.
  * Шаг 1: Order Service резервирует книгу.
  * Шаг 2: Payment Service обрабатывает платеж (с использованием ключей идемпотентности).
  * Compensating Action: Если оплата не прошла, Saga отправляет команду UndoBookReservation, возвращая книгу в продажу.

Connective Tissue: Эти механизмы превращают «желаемую» надежность в «гарантированную», исключая потерю данных даже при падении брокеров сообщений или сетевых сбоях.

6. Стратегия полнотекстового поиска

Поиск в Telegram — это 90% пользовательского опыта. Мы используем гибридный подход на базе PostgreSQL.

* Сравнение: tsvector обеспечивает отличную морфологию, но для Telegram-ботов критичен pg_trgm (триграммы), так как пользователи часто совершают опечатки.
* Trade-off: Хотя GIN-индексы для триграмм на 100M записей имеют высокую стоимость записи и объем, для нашего Read-heavy профиля (QPS 23,000 на чтение против QPS 100 на запись) это оправдано.
* Оптимизация: Для защиты Master-ноды от нагрузки поисковых запросов мы внедряем Read-only Slaves. Поисковый сервис направляет трафик только на реплики, оставляя Master для критических транзакций записи заказов.

Connective Tissue: Данная стратегия позволяет начать с надежного решения на PostgreSQL без преждевременного усложнения архитектуры кластерами Elasticsearch (принцип YAGNI).

7. Анализ узких мест и стратегия масштабирования

Проектирование завершается анализом пределов роста и устранением единых точек отказа (SPOF).

* Sidecar Proxies: Для offloading-задач (логирование, mTLS, аутентификация) рядом с .NET сервисами разворачиваются Sidecar-контейнеры (Envoy). Это освобождает бизнес-логику от cross-cutting concerns.
* Horizontal Sharding: При исчерпании возможностей Master-Slave репликации PostgreSQL, мы переходим к шардированию по user_id, распределяя данные между физически разными кластерами.
* High Availability: Балансировщик YARP разворачивается в Active-Passive конфигурации. Репликация S3 между регионами обеспечивает сохранность медиа при катастрофических сбоях дата-центра.

Итоговый вывод: Предложенная архитектура на базе .NET 8, Orleans и YARP полностью покрывает требования по нагрузке в 100M DAU. Использование паттернов Saga и Outbox гарантирует целостность данных, а асинхронный пайплайн медиа обеспечивает Latency < 200ms, делая платформу надежным инструментом для вторичного рынка книг.
