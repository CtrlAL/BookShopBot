# ADD Task Runner

Запускает автономную ADD-задачу: превращает описание пользователя в спецификацию
`.tasks/current_task.md` и прогоняет через `scripts/tdd_loop.py` — цикл «агент +
валидация» с жёсткими инвариантами. Агент вызывается один раз за шаг, после чего
репозиторий проверяется в фиксированном порядке: `dotnet format` (линтер),
`dotnet build -p:WarningsAsErrors=CS*` (типизация/компиляция), `dotnet test` (тесты).
При падении стектрейс (обрезка 2000 символов) возвращается агенту; максимум 4
самоисправления, после чего — Circuit Breaker и контроль над человеком.

## Когда использовать

- Пользователь просит «запустить / выполнить / сделать задачу (таск)» автономно.
- Есть готовый `.tasks/current_task.md` и нужно прогнать цикл.
- Надо оформить спецификацию задачи по шаблону перед циклом.
- Стек репозитория — C# / .NET; все команды валидации строго фиксированы
  (см. `.opencode/rules.md`).

## Предусловия (быстрая проверка перед стартом)

Проверь, что все на месте; если чего-то нет — остановись и сообщи, что добавить:

- `scripts/tdd_loop.py` существует (фреймворк развёрнут);
- `.tasks/template.md` существует (структура спецификации);
- `BookShop/BookShop.sln` существует (целевое решение);
- доступны `dotnet` (8+) и `python` (3.10+).

## Рабочий процесс

### Шаг 1. Понять описание задачи

Возьми описание из запроса. Если оно размытое — задай 1–2 уточняющих вопроса
(это ДО цикла, интерактивность здесь разрешена). Нужно выяснить минимум:
что делаем, как проверить, какие файлы трогаем. Если пользователь дал чёткое
ТЗ — не переспрашивай, переходи к Шагу 2.

### Шаг 2. Подготовить спецификацию `.tasks/current_task.md`

- Спецификация ЕСТЬ и покрывает текущую задачу → повторно использовать.
  Покажи пользователю краткую сводку (в 5 строк) перед запуском.
- Спецификация ЕСТЬ, но это другая задача → предупреди, что файл будет
  перезаписан; сделай бэкап в `.tasks/.tmp/current_task.<YYYYMMDD-HHMMSS>.md`.
- Спецификации НЕТ → создай из `template.md`. Заполни разделы:

  - **Context & Objective** — парафраз описания пользователя, 2–4 строки.
  - **Interface Contract** — конкретные сигнатуры (C#). Если пользователь не
    знает типы/названия — предложи разумные дефолты и подтверди с ним.
    Никакого «прозы», только псевдокод сигнатур. Если задача не меняет
    публичный API — строго `N/A`.
  - **Acceptance Criteria** — чеклист: (1) сперва падающий тест в `tests/`,
    (2) `dotnet build` без ошибок, (3) `dotnet format --verify-no-changes`,
    (4) нет регрессий, (5) пункты предметной задачи.
  - **Affected Files** — СТРОГИЙ белый список (таблица «файл → действие»,
    создание/изменение). Включи тестовый файл и целевой исходник. Сомневаешься —
    добавь строку ДО запуска: Scope Guard запрещает трогать файлы вне списка.

  Во время подготовки ЕДИНСТВЕННЫЙ файл, который ты создаёшь/меняешь —
  `.tasks/current_task.md` (плюс бэкапы). Код реализации не трогай.

### Шаг 3. Запустить цикл

```bash
python scripts/tdd_loop.py
```

Маппинг флагов по пожеланиям пользователя:

| Пользователь сказал | Флаг |
|---|---|
| «без тестов», «не TDD», «просто сделай» | `--no-require-tests` |
| «проверь только текущий статус» | `--no-baseline --agent-cmd "python -c \"pass\" {prompt}"` |
| «другой агент» например `claude` | `--agent-cmd "claude --print {prompt}"` |
| «начни с чистого restore» | сначала `dotnet restore BookShop/BookShop.sln`, потом цикл |

По умолчанию: до 5 итераций, 4 самоисправления, `opencode run {prompt}`,
требование тестов включено. НЕ добавляй произвольные флаги — только если
пользователь явно попросил.

Цикл не спрашивает вопросов — он неинтерактивен по построению. Ты передаёшь
ему готовую спецификацию и ждёшь завершения процесса.

### Шаг 4. Интерпретировать результат

Прочитай код выхода:

- **0** — все стадии валидации прошли. Покажи сводку: что реализовано, какие
  проверки пройдены (format / build / test), что изменено (по строкам
  Affected Files). Не заявляй успех без exit=0 (verification-before-completion).
- **1** — Circuit Breaker: лимит попыток исчерпан или агент не вышел в ноль.
  НЕ начинай самостоятельную починку внутри скила по умолчанию — выведи отчёт
  (последняя ошибка, что пробовалось, затронутые файлы) и передай управление
  человеку. Если пользователь попросит — можешь починить вручную и прогнать
  цикл повторно.

### Шаг 5. Что дальше

После успешного захода напомни про защиту от регрессий: `git add .` и `git commit`
вызовут pre-commit хук (тот же пайплайн format → build → test), который заблокирует
коммит при падении. Обход только осознанный: `git commit -n`.

## Инварианты (запрещено обходить)

См. `.opencode/rules.md`. Ключевые:

1. **TDD Invariant** — нельзя менять код реализации до падающего теста.
2. **Scope Guard** — только файлы из белого списка.
3. **Non-Interactive Rule** — в цикле не задавать встречных вопросов.
4. **Deterministic Verification** — только фиксированные команды из rules.md.
5. **Circuit Breaker** — максимум 4 самоисправления, дальше человек.
